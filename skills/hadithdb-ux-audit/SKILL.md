# HadithDB UX audit

Start with the current page and the [component library](../../docs/design-system/library.html). The [audit atlas](../../docs/design-system/index.html) helps locate equivalents across routes. The library records accepted designs. After selection, fold the chosen treatment into its existing entry, refresh affected specimens, and retire the comparison files and styles after checking their consumers. Keep original audit captures available for before-and-after review.

Use standard URLs on the active checkout. The makeover is on master. Use the pre-merge revision for historical comparisons. Switch collections, reload, verify return links, and check route-specific assets and cached HTML.

## Inspect two ways

1. **Walk the page by task.** Inventory the panels, controls and routes that share the view. Read the template and client renderers to find elements that appear after loading, signing in, connecting an account, opening a nested disclosure, changing view, or enabling a feature. Map these to the states the user can actually reach. Use local fixtures for account writes and gated services. Record any state you could only inspect in source.
2. **Walk across the page by control family.** Open comparable surfaces with the same viewport, theme, data and interaction state. Put the rendered controls side by side. Include panel headers and toolbars, fields and unit suffixes, switches and favorites, links and buttons, cards and rows, disclosure indicators, and inline feedback wherever present. For a new page, look for additional families specific to its tasks.

Check desktop and phone. Look at hierarchy, wrapping, alignment, typography, spacing, and affordances in context. Use the DOM to resolve differences that a screenshot can hide: bounding boxes for height and alignment, computed colors for checked and focused states, and the accessible name, role and selected state. Inspect the winning CSS rule and its owner before changing it. Bootstrap layout utilities can implement an approved pattern; a familiar class name alone tells you little about the rendered experience.

## Turn a discrepancy into a decision

Track a short working record per family: **surfaces compared · states viewed · observed difference · intended shared pattern or reason to differ · verification**. Use scratch notes or screenshots during the audit. Report consequential differences and coverage gaps to the user.

Concrete Settings comparisons to carry forward:

- **Fields.** Compare a Review number input and its attached “minutes” suffix with a Billing select and threshold input. Measure rendered heights, check label baselines, and narrow the panel until the grid wraps. Test focus and disabled states.
- **Switches and actions.** Compare a checked catalog switch with connected Drive and auto-recharge switches. Check the track color, size and visible label. In Drive, exercise disconnected and connected states to reveal the primary Connect, secondary Import, and lightweight folder and disconnect actions.
- **Disclosure alignment.** Compare the first line of expanded content with the disclosure label itself, including when the label wraps next to a primary action. Check top and bottom padding with the panel open.
- **Control-to-label spacing.** Measure from the painted control edge to the first line of label text in the rendered UI. Padding on a wrapper can be canceled by a floated input or negative margin. Compare a short label with a wrapping one at phone width and enlarged text. Check that continuation lines align with the first word, the switch stays beside the first line, and clicking the label still toggles it.
- **Round trips and feedback.** When a return link focuses a section by fragment, activate an in-place action there and verify focus stays on its control after the update. Enter a shared destination from each parent route, then use its visible Back link. Verify the originating panel is open and visible, including its Quran variant. Where one page mixes explicit-save and immediate actions, verify each result appears beside the controls that triggered it.
- **Bilingual heading alignment.** Measure font size on the element containing the visible text, including editable spans that match language-specific rules. Measure the Arabic text’s right edge against the main column in both the shared-row and stacked layouts.
- **Type hierarchy across routes.** Compare a catalog with the accepted reference page at identical desktop and phone widths. Measure computed type on global and local navigation, rail titles and links, page and group headings, item titles in each script, metadata and badges. When two roles should match, record both computed values at identical viewports and assert equality for family, size, weight and line height. For page titles, run `node skills/hadithdb-ux-audit/scripts/compare-titles.js /settings /books` against the local server. The check fails if any computed value differs. Check the intended size and weight difference between primary navigation and local navigation in both active and inactive states. Compare section-title dividers and mobile content gutters alongside the type measurements. Inspect paired English and Arabic titles together, including diacritics and long names. For Arabic weight changes, inspect the rendered font face for regular, medium, bold and honorifics in a browser, including mixed-script print and editor text. For Quran text, check bold markup around a nested word and inside a selected verse, and verify the Indo-Pak and Warsh choices still render their own faces. Toggle edit mode on the same reader and inspect computed fonts on the bound English field, its nested text, the Arabic field and save feedback. Compare perceived size at normal reading distance. Put short and long bilingual names in adjacent cards at the same width. Check their row placement, Arabic alignment and whether a size indicator wraps onto a line by itself. Check whether static metadata looks clickable alongside real controls. Inspect the rendered page for headings that read like ordinary rows even when their tap targets are large. Compare the actual font faces of English and Arabic breadcrumb links, and measure caption text inside nested muted elements. Measure the actual English narration paragraph inside the Hadith Markdown body and the inline commentary at normal and enlarged reader zoom, on phone and desktop.
- **Overlay dismissal.** Compare the X on a drawer, a native dialog and a Bootstrap modal, including dynamically built overlays. At matching widths and themes, inspect the glyph, target, focus ring and hover surface. With sibling actions, check the gap to Close for short and long titles in regular, expanded and floating layouts. Activate the X and verify focus returns to the opener. Run `node skills/hadithdb-ux-audit/scripts/compare-overlay-close.js` against local Books.
- **Spacing inside compound controls.** Measure both inner edges in the rendered control, from its boundary to the leading icon and trailing accessory. Compare those distances with the intended insets at the breakpoint and at a wider viewport. Check the winning CSS when dimensions differ. Compare both painted insets when the shortcut is visible and check icon centering when the search collapses. For the header, run `node skills/hadithdb-ux-audit/scripts/check-search-insets.js` against the local app.
- **Site-wide shell changes.** Trace public HTML and direct aliases as well as shared templates. Follow the legal links from the footer. Check one masthead and footer per app page, loaded palette tokens, contextual search, and the header on a cached reader URL. Distinguish standalone documents and feeds from pages that use site navigation.
- **Shared navigation.** Compare the order of the masthead, subnav, page title and first section across standard and Quran variants. Check both edges of the subnav against the viewport on a phone and above the primary header’s maximum width. On routes with a fixed header, measure how much of the first phone viewport remains for content. Open a later collection directly and check that its active tab is visible. Measure immediately below and above each breakpoint, then repeat after scrolling. Check a subnav with a nonzero unread count and compare its row height with Books. Check icon hit areas, drawer focus and Escape return, including overlap with persistent bottom controls. Compare the footer height, surface and type scale with the last content section on desktop and phone. Compare footer placement on a short collection, an empty search result and a long list. Check the space reserved for fixed bottom navigation. At the end of the list, activate footer links above the bottom controls.
- **Dropdowns.** Inspect the closed picker icon beside its actual selected label, including Bootstrap fields, compact translation controls and bilingual admin grades. Check the grader stays visible when the row wraps. Compare computed hover, keyboard focus and current-location styles across drawer, rail and avatar rows in both themes, including image icons. Inspect an opened menu with a long account name, a current destination, and conditional admin controls. Compare the identity, destination and action weights, icon alignment, separators and touch targets. Check viewport fit, arrow navigation and Escape focus return on desktop and phone.
- **Navigation drawers.** Compare the open drawer with a reference right rail at the same viewport. Measure computed title, tab, filter, row and status typography, filter height and menu targets. Check both scripts in bilingual rows and confirm the palette reaches overlays outside the page container.
- **Right rails.** Compare the computed size and weight of the previous, current and next chapter (including the link inside the menu), a section and a nested link after the shared menu styles load. Inspect both the list edge and the current row for legacy borders, then check the keyboard focus ring. On three-column pages, check update dates, titles and populated status messages against both rails above and below the author-rail breakpoint and while scrolling. Compare the visible title wording, heading level, interactive role, computed ink and typography across equivalent rails. Check which title persists on collection switches. Compare the page-title and rail-title boxes, their clearance below the rendered header, and the space to the next section or search field. Check initial load, collection switches, wrapped headings and the stacked mobile layout. On the collapsed Quran mode bar, compare control heights and verify the picker chevron stays beside the longest label at 320 px and across the collapse breakpoint. On Quran routes measure clearance below the mode bar, open the script menu, and follow a mode switch at the current āyah. Check redirected catalog entrances as well as readers and Mudhakkir. Compare the rail’s left edge, width and sticky offset across routes. Measure the local filter’s edges inside the rail and compare its empty, focused and populated states, including the clear control. In the stacked layout, measure the filter against both edges of the content and compare the gap to the first section. Resize through the desktop breakpoint with a filter active and confirm the same controls and results remain available.
- **Task order and heading rank.** Measure the gap between a local filter and its first result after shelves or toolbars are inserted. - **Directory variants.** On covers, check the longest vocalized title against the inner frame and icon at phone and desktop widths. - **Reader margins.** Compare the left and right edges of the actual main reading area on Study, Tafsir and Hadith at phone width and on either side of each grid breakpoint. Measure the heading rail separately.
- **Book contents.** Scroll across two sections in the same chapter and into the next chapter. In the full-screen Mushaf, drag from a word to outside the sheet, swipe both ways on touch, and test horizontal wheel input, vertical scrolling and single-word taps separately. Compare the full-screen opener’s rendered fill, icon color, border and dimensions with the translation control. Measure long Arabic lines against both sheet edges after an animated turn. Follow both language breadcrumbs back to the selected source tab, including a link to a collapsed section. Check Muslim i001 as well as a regular chapter. Compare the introduction rail, active section and picker choices with the linked SQL records. Check virtual source numbering against its physical reader reference. On the detail page, check that the collapsed preview contains only the opening Arabic body text, then expand and collapse it at phone and desktop widths. Check the actual table edges and last Arabic cell against phone gutters, expand a nested chapter, clear a filter, and follow a reader link back. Compare title and rail offsets on Quran and Hadith routes because their mastheads can have different heights. Compare the entire first viewport with Books at 700/701 and 991/992 px. - **Toolbars.** Check closed feed filters with short and long selected values. Measure the height of each trigger and verify its chevron stays beside the label as the toolbar wraps. Trace the CSS hierarchy from foundation token to component to route layout. Search for existing rules and all consuming templates before adding a selector. Consolidate competing definitions at their owner, scope route-specific layout locally, and check the winning declarations in the browser on each affected surface. On the reported deep link, compare the stylesheet URL from the running app with the current build and check the computed style after a normal reload. A fresh browser can fetch updated CSS under an obsolete URL and mask a stale cached copy.

Reuse the accepted component or shared CSS owner when the tasks match. Preserve distinctions such as immediate versus explicit save, Quran script typography, and semantic links versus buttons. For a proposed visual direction, record it as a candidate until selected. When a pattern is finalized, add its real specimen, states, implementation hook and consumers to the library, or extend its existing entry.

## Verify and maintain

For share images, open the exported PNG and compare its frame and script artwork with the preview. A loaded SVG in the DOM can still be cropped by the canvas renderer.

Revisit the same surfaces and states after edits. Check keyboard operation, focus, and the affected behavior (for example reload persistence, rollback, or return navigation). Record visual comparisons separately from functional tests. A passing save test cannot establish that two fields align.

For public documents, parse the initial response across the route inventory. Compare canonical URLs, social tags and the JSON-LD page entity, then repeat after a catalog switch or a lazy reader transition. Check error and shared-link responses for unintended indexing or disclosure.

Before retiring a template, trace its mounted route, parent includes, conditional render targets, fragment endpoints and cached HTML producers. Check test-only callers against the current route and exercise its replacement with fresh HTML.

For cross-route changes, compare the full Jest run against a pre-edit baseline. Run `npm run test:frontend` against the local app and both `npm run test:frontend:admin` and `npm run test:frontend:personal` with intercepted writes. Verify public readers have no bound editing controls, and check initial and dynamically inserted admin fields, RTL, failed-save retry, dialog dismissal and explicit versus immediate submission.

At the end of each makeover page, and whenever the user identifies a miss, review this skill. If the work exposed a reusable blind spot, add the smallest comparison that would have caught it and how to verify it. Merge overlapping guidance. Keep design values and component specimens in the library, and keep audit methods here. Make warranted updates alongside the page change.
